# ADR 0003：Phase 0 实测结论

- 状态：已实测（2026-11-13，Claude Code 2.1.322）
- 脚本：Phase 0 的验证脚本依赖作者自己的工作区，只在作者本机留存，没有放进公开仓库。

## 结论

ADR 0001 成立：spawn `claude -p`，审批走 MCP 工具，这条路走得通。实测多出来五条硬约束，已经写进 plan.md：

1. **必须显式传权限模式，并按模式设计审批。** 2026-11-13 已定用 auto。
   - 精简环境不读用户级设置，所以要显式传 `--permission-mode auto`。
   - auto 下，分类器会放行 prompt 里明说要做的事，审批工具收不到。所以「我说一句」档必须写成 `ask` 规则，「只能我」档必须写成 deny 规则。这两类规则在 auto 下照样生效，见 ⑤。
2. **必须用干净的环境变量启动 claude。** 从 Claude Code 里面拉起的子进程会继承约 30 个变量（`ANTHROPIC_BASE_URL`、`CLAUDE_CODE_*` 等），交互式会话还会因此关掉 transcript 保存。干净环境下，claude 用的是本机 CLI 自己的登录（`apiKeySource=none`，也就是订阅登录）。
3. **分诊类路由用 `--setting-sources project,local` 跑精简环境。** 冷启动从 3.4 s 降到 0.5 s，一次空问答的花费从 $0.33 降到 $0.0004（按 API 价折算）。两级 CLAUDE.md 照样加载。
4. **批准过的调用，resume 时要自动放行；还在等审批的调用，再请求就立刻拒。** 被拒后 resume，agent 会把同一个调用再请求一次。被拒后不 resume，模型也可能马上重试（30 分钟那次就是这样）。CLI 等审批工具至少能等 30 分钟，不会超时。
5. **deny 后从 `result.permission_denials` 判断。** 被拒的调用会结构化地列在这里，daemon 据此把任务转为待审批，不用解析文字。

另外三条影响设计、但不是 runner 选型的结论：

6. **组合命令要靠审批工具拆开判断。** allow 规则按前缀匹配，`cd 仓库 && gh pr view …` 匹配不上。
7. **旧结论不能进 prompt。** agent 看到账本里的旧草稿会照抄。
8. **分诊上 sonnet 没有比 deepseek 好。** 逐条跑约贵 14 倍，合批约贵 3 倍，但合批几乎不查证据。后来已定拆成三段：规则 → haiku 判断要不要处理 → Opus 5.5 medium 处理。haiku 第一段的实测见 ⑥。
9. **合批输出要用短序号核对。** haiku 往回抄长 id 会抄错，202 条里有 25 条因此对不上号（⑥）。

## ① 审批

| 场景 | 结果 |
|---|---|
| 不传 `--permission-mode` | 继承用户级 auto，审批工具没收到请求，命令直接执行了 |
| 传 `default`，5 s 后批准 | 原地继续，命令执行，exit 0 |
| 20 s 没人批 → 审批工具返回 deny | 这一轮正常结束（exit 0，`subtype: success`）。被拒的调用列在 `result.permission_denials`（tool_name、tool_use_id、tool_input）里。agent 照原文转述了 deny 的 message，没有换办法绕过 |
| deny 后 `-p --resume` 并告知已批准 | agent 重新请求同一个调用，2.5 s 后批准，完成 |
| 挂起 20 分钟没人批（干净环境） | CLI 一直等，没有超时。20 分钟后审批工具返回 deny，这一轮正常结束，总耗时 1207 s |
| 挂起 30 分钟没人批（继承了 desktop 环境变量） | 同样没超时。但 deny 之后，haiku 立刻把同一条命令又请求了一次，开始新一轮等待，我手动停掉了 |

**挂起时长不是问题**：至少 30 分钟，CLI 都不会自己掐断审批工具的调用。

**真正的问题是模型被拒后可能重试。** 同样的 prompt，20 分钟那次停下了，30 分钟那次又请求了一遍。所以审批工具要记住：刚被拒、还在等审批的同一个调用（tool_name 和 input 都相同）再次请求时，立刻再拒，不重新计时。

- **审批工具收到的入参**：`{"tool_name": "Bash", "input": {"command": "...", "description": "..."}, "tool_use_id": "toolu_..."}`。
- **审批工具的返回**：一个 text 块，内容是 JSON 字符串，`{"behavior":"allow"}` 或 `{"behavior":"deny","message":"..."}`。

## ② 接管

| 步骤 | 结果 |
|---|---|
| `-p --session-id <uuid>` | 会话 id 就是传进去的这个，`system/init` 和 `result` 里都对得上 |
| 终端里 `claude --resume <uuid>`，聊一轮后 `/exit` | 接着原会话聊，没有分叉出新 id。transcript 记在 `~/.claude/projects/<cwd 编码>/<uuid>.jsonl` |
| 再 `-p --resume <uuid>` | 能看到 headless 和交互两轮的内容（两个暗号都答对了） |

两个坑：

- **信任对话框。** CLI 的「信任此文件夹」记录在 `~/.claude.json` 里，和 desktop app 不共用。在 CLI 没信任过的目录接管，会先停在信任对话框，由人点确认。profile 根目录一般都信任过。
- **环境变量。** 从 Claude Code 会话里拉起的交互式子进程，会继承 `CLAUDE_CODE_CHILD_SESSION`，提示「Transcript saving is off」，接管的那一轮不会被记下来。daemon 由 launchd 启动，本来就是干净环境；开发时从 Claude Code 里跑 daemon，也必须清理环境变量。

## ③ 分诊质量和花费

**做法**

- **样本**：从现有收件队列的账本里固定抽 8 条：旧流程（opencode + deepseek）起草过的 5 条，关掉的 3 条。
- **新流程**：用 `claude -p`（sonnet、精简环境、只读）一条一条重放。
- **对照**：旧流程的结论，以及**我后来实际有没有回、回了什么**。后者当作标准答案。

**跑了三次，前两次作废**

| 次 | 问题 | 结论 |
|---|---|---|
| v1 | allow 规则按前缀匹配，agent 写 `cd 仓库 && gh pr view …` 被拦，查不到证据，草稿只剩「收到，我确认下」 | 作废。教训：权限要能处理组合命令，见 plan.md §7 |
| v2 | `cli.ts item` 会返回账本里旧流程的草稿和证据，sonnet 照抄，有两条一字不差 | 作废。教训：重放或评测时，旧结论不能让 agent 看到 |
| v3 | 条目详情直接写进 prompt，禁止读账本 | 有效 |

**v3 结果**

| 消息类型 | 我实际 | 旧（deepseek） | 新（sonnet） | 谁更好 |
|---|---|---|---|---|
| 同事请我验收已发 staging 的改动 | 回了「没问题直接发」 | 起草「收到，验完回你」 | 同左 | 持平 |
| 同事问我的 PR 能否随今天的车发 | 回了「可以发」 | 起草事实，加「发不发我确认下」（守住了「排期我拍板」的红线） | 起草「可以，跟车发吧」（和我的决定一致，但越过了红线） | 各有得失 |
| 技术方案评审，@我 | 回了两个具体技术问题 | 读了代码，起草两点具体意见，和我后来问的点吻合 | 只起草一句「我对一下再回你」 | 旧更好 |
| PM 问别的团队的修复要不要加急 | 没回 | 起草一句不含承诺的话 | 关掉，不归我 | 新更好 |
| QA 让我看某产品在 OS 上的可用性 | 回了我负责的那部分没受影响 | 查了日志，起草较长的结论 | 起草「不是我的产品线，去问别人」 | 旧更好 |
| bot 的操作指令 | 没回 | 关掉 | 关掉 | 持平 |
| 发版完成通知 | 没回 | 关掉 | 关掉 | 持平 |
| 别人被 @ 的后端接口问题 | 没回 | 关掉，不归我 | 跑了 20 轮读别人的后端代码，替人起草了答案 | 旧更好 |

- **该不该回**：两边都是 7/8 和我的实际一致。
- **草稿质量**：旧流程好 3 条，新流程好 1 条，各有得失 1 条，持平 3 条。
- **花费**（按 API 价折算）：
  - sonnet 逐条跑，平均 $0.283/条（$0.24–$0.46），每条耗时 36–179 s。
  - 旧流程按 opencode 的统计，14 天 $3.80，约 200 条，合每条约 $0.02。旧流程是 8 条合成一次跑的。
  - 合批的效果见下面 ③b。

**结论**：这 8 条样本上，sonnet 做分诊没有比 deepseek 好，逐条跑的花费约是它的 14 倍。sonnet 最严重的一次错误是替别人回答问题，这是 skill 和决策模型的缺口（「@ 的不是我」这条没写硬），应该在 profile 里修，不是引擎的问题。

**③b 合批**：同样 8 条、同样的权限，放进一次 `claude -p` 跑，和旧流程一样合批。

| | 逐条（v3） | 合批（③b） | 旧流程 deepseek |
|---|---|---|---|
| 每条花费（按 API 价折算） | $0.283 | $0.057 | 约 $0.02 |
| 总耗时 | 8 次并发 4，单条 36–179 s | 79 s | — |
| 该不该回，和我的实际一致 | 7/8 | 7/8 | 7/8 |
| 草稿 | 有两条查了证据 | 全是「收到，我看下再回你」这一类，8 条一共只跑了 12 轮，几乎没查证据 | 证据最扎实 |

合批把花费压到逐条的 1/5，但 agent 把一轮预算摊薄了，几乎不查证据。上一版里替别人答题的那条，合批时判对了「不归我」。

**对设计的影响**，已写进 plan.md：

- **分诊分两段。** 第一段合批，只判「回不回、归不归我」并起草不含承诺的一句，便宜。判为「要回且要查证据」的条目，第二段单独开会话深做。这正好对应 plan.md §5「分诊批量跑，深做单独跑」。
- **模型怎么选要拍板。** 分诊先用 sonnet 是之前定的，但实测下来，sonnet 合批的每条花费仍是 deepseek 的约 3 倍，质量没有更好。可选：一期就用 sonnet 合批；或者第一段换 haiku 再测；或者 runner 提前接 opencode。

## ⑥ 第一段：haiku 只判断要不要处理（2026-11-13 补测）

**做法**

- **样本**：账本里全部 202 条消息。daemon 先替每条拉一次上下文，把原文、前 6 条消息、是否 @ 我、我之前在这个对话里有没有说过话喂给 haiku。
- **调用方式**：haiku 不给任何工具，20 条一批，判断口径是工作区的决策模型和角色说明。
- **标准答案**：这条消息之后，我在同一个对话里有没有说过话。这个标准偏松：我后来说的话可能是在回别的消息，所以 haiku 的真实召回率比下表高。

**结果**

| 方法 | 判为要处理 | 召回（我回过的里抓到几成） | 精确 | 花费 |
|---|---|---|---|---|
| haiku 第一段 | 83 / 177 有结论的 | 0.64 | 0.70 | 10 批共 $0.099，每条约 $0.0006 |
| 旧流程（起草了就算处理） | 85 / 202 | 0.55 | 0.68 | 每条约 $0.02（含起草） |
| 纯规则：thread 只 @ 别人就跳过，其余全处理 | 141 / 202 | 0.78 | 0.58 | 0 |

- **haiku 漏掉的 33 条**：抽查下来大多是发版通知、「好的」「辛苦」这类收尾、明确在问别人的消息。我后来的回复多半是在回同一个对话里的别的消息。漏掉的 DM 和 @我 只有 5 条，都是通知类。
- **上一轮 sonnet 替别人答题的那条**：haiku 判了不处理，理由是「问的是另一位同事，已有答复」。
- **有 25 条 haiku 没给结论**，其中 24 条是 thread。这些 thread 的 id 是三段长数字，haiku 往回抄的时候抄错了，对不上号。改成用 1..N 的短序号重问，25 条全部有结论。复跑这 25 条花了 $0.0074。第一次跑的时候出现过一次 $0.37，原因未核实。

**「thread 新回复只 @ 了别人」不能当硬规则。** 这类消息共 61 条，其中 23 条（38%）我后来还是回了。所以这个信号只作为特征喂给第一段，不在代码层直接丢掉。

**对设计的影响**

- **合批的条目用短序号，不用账本 id。** 拿回结果后逐条核对，缺的单独重问。这一条就是喜好里写的「LLM 输出当不可靠输入」。
- **第一段用 haiku 就够。** 召回高于旧流程，花费只有旧流程的约 1/30。

## ⑦ 规则对变体写法管不管用（Phase 1 补测）

auto 模式加审批工具，命令全部是无害构造：push 推到本地裸仓，slackcli 带 `--dry-run`，收件人是我自己。

| 命令 | 规则 | 结果 |
|---|---|---|
| `git push origin main` | ask `Bash(git push:*)` | 出卡 |
| `cd 目录 && git push origin main` | 同上 | 出卡（Claude Code 会拆开组合命令） |
| `git -C 目录 push origin main` | 同上 | **漏了**，auto 直接放行，推成功 |
| `git -C 目录 push origin main` | 再加 ask `Bash(git -C * push:*)` | **还是漏了**：规则中间的通配符不生效 |
| `slackcli messages send …`、前面加 `cd /tmp &&`、前面加环境变量 | deny `Bash(slackcli messages:*)` | 都拦住了 |

**补救：`sidekick guard`，一个 PreToolUse hook。** hook 在规则之前判断，它做这几件事：

1. 把命令按 `&&`、`;`、`|` 拆段。
2. 去掉环境变量前缀和 `env`、`sudo` 这类包装。
3. 把 `git -C`、`git -c` 这类全局参数折叠掉。
4. 对 `bash -c` 和 `eval` 往里看一层，含变量看不清的一律要求审批。

处理完再对照 profile 的 ask 和 deny 规则。用真实 claude 复测的结果：

- `git -C 目录 push`：出卡。
- `bash -c "slackcli messages send …"`：被拦。
- `git -C 目录 log`：照常放行。

**已知的残余风险：** agent 和 daemon 是同一个系统用户。它要是用 python 或 bun 直接写账本，把自己的审批改成「已批准」，规则和 hook 都拦不住，只能靠 auto 分类器判断。后续可以用 Claude Code 的沙箱，把 `.state/` 设成只读来补上。

## ⑤ auto 模式（2026-11-13 补测）

精简环境，`--permission-mode auto`，haiku，挂着审批工具（3 s 后自动批准），三条命令都是无害构造：

| 命令 | 额外规则 | 结果 |
|---|---|---|
| 写本地文件 | 无 | 分类器放行，审批工具没收到请求 |
| `git push --force` 到 out/ 下的本地裸仓 | 无 | 分类器放行，审批工具没收到请求 |
| 向 `example.invalid` 发 POST | 无 | 分类器放行，审批工具没收到请求（请求本身在 TLS 握手阶段失败） |
| 同上 force push | `--disallowedTools "Bash(git push:*)"` | 被拦，记在 `permission_denials` 里 |
| 同上 force push | `--settings` 里写 `permissions.ask: ["Bash(git push:*)"]` | 交给审批工具，批准后执行 |

结论：

- prompt 里明确要求的事，auto 分类器会当成已授权，直接放行。
- deny 规则和 ask 规则排在权限模式之前判断，auto 下都照样生效。

所以三档授权这样落地：

| 档 | 落到哪 |
|---|---|
| 自主 | auto 分类器 |
| 我说一句 | ask 规则 → 审批卡 |
| 只能我 | deny 规则 |

## ④ 配置隔离

在工作 profile 根目录，干净环境，haiku，`--tools ""`，问三道判断上下文的题：

| | 默认 | `--setting-sources project,local` |
|---|---|---|
| 冷启动（到 init 事件） | 3.4 s | 0.5 s |
| 总耗时 | 13 s | 6 s |
| MCP 服务 | 77（18 个已连上，大部分是 claude.ai 连接器） | 0 |
| 工具 | 317 | 0 |
| skill | 104 | 19 |
| 插件 | 11 | 5（组织统一下发的，去不掉） |
| 花费（按 API 价折算） | $0.33 | $0.0004 |
| 用户级 CLAUDE.md | 加载 | 加载 |
| 项目 CLAUDE.md | 加载 | 加载 |

精简环境会丢掉以下内容，plan.md 里已经做了对应处理：

- **用户级 skill。** 工作区的 skill 是软链进 `~/.claude/skills` 的，精简环境下不注册。处理办法：路由里写 skill 文件的路径，prompt 里让 agent 先读这个文件。现在的 slack-inbox 就是这么做的。
- **用户级权限。** auto 模式，以及 46 条 allow 规则（含 `git commit`、`git add`）。正好不想让它们进来。
- **claude.ai 连接器**（Jira、Slack、Notion 等 MCP）。需要它们的路由（比如工单闭环读 Jira）走完整环境，或者用 `--mcp-config` 显式给。
